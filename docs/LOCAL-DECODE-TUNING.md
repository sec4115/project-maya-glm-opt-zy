# 本机 GLM 解码实验

本次上游基线为 Project Maya 1.1.25，提交
`8412d5edc36e714ea4001a56c5bb65a7b2228d41`。完整源码、升级前备份、
逐项测试配置与实测数据保存在 `bench/results/optimize-20261023/`。

下面的新增选项均默认关闭。用户配置可使用 `MAYA_` 名称，直接调用引擎时
使用对应的 `STRATA_` 名称。请依据同模型、同上下文、同实际缓存容量的对照结果选用，
不要将增加 RAM 缓存的收益算成代码提速。

本机 2026-10-24 初始双卡配置为 RTX 5090 D + Tesla PG500-216（sm_120 + sm_70），两卡各 32 GiB。
三种 GLM Flash 尺寸都使用 GPU 列表 `[0, 1]`、140 GiB RAM 专家缓存、GPU1 专家池上限 24 GiB，
GPU0 预留 1024 MiB，CPU lane 为共享的 10 线程，启用 `MAYA_GLM_ZERO_COPY=1`。
本次使用 CUDA 12.9.41，二进制同时包含 sm_70 与 sm_120；CUDA 13.x 不支持离线生成 sm_70。
修复了 Windows 环境缺少处理器架构变量时 GGML 误选通用 CPU 实现的问题：
仅在系统架构为空且 MSVC 已确认 x64 编译目标时补全 AMD64，由 GGML 正常探测 CPU 指令集。

XL 的三组 128-token 短解码为 17.13 / 19.39 / 18.89 tok/s，合计 18.41 tok/s。
同二进制、同显存预算的分卡 PCIe 分流试验为 18.02 tok/s，未采用。
M/L 只同步硬件配置，未启动或测速。本次短测试未覆盖长上下文与实际视觉请求。
详见 [双卡测试报告](../bench/results/pg500-20261024/REPORT.md)。

| 环境变量 | 用途 |
| --- | --- |
| `MAYA_GLM_ZERO_COPY=1` | 将每步的少量嵌入输入、路由表更新与 token 输出映射到锁页主机内存，减少显式 CUDA 拷贝。专家权重仍走原有缓存与搬运路径。 |
| `MAYA_GLM_CPU_PLAN0`、`MAYA_GLM_CPU_PLAN1` | 按 GPU 指定 CPU 专家计划。必须为九位数字，第 f 位表示 f 个 RAM 专家中交给 CPU 的数量，取值 0..f。未指定时回退到全局 CPU_PLAN 与自动计划。 |
| `MAYA_GLM_PCIE_SHARE0`、`MAYA_GLM_PCIE_SHARE1` | 按 GPU 指定 RAM 专家经 PCIe 交给 GPU 的比例，取值 0..1；未指定时回退到全局值。 |
| `MAYA_GLM_CPU_BATCH_CAL=1` | 启动时测量 CPU 同时计算 1..8 个专家的总成本，替代线性估算。显式 PLAN/SHARE 优先，不覆盖用户指定值。 |
| `MAYA_GLM_CPU_JOINT_CAL=1` | 在 GPU 搬运、GPU 专家计算和 CPU 专家计算并行时测量总成本。只有测得同时超过 3% 与 5 微秒的改善才调整计划。增加启动时间。 |
| `MAYA_GLM_WAIT_FETCH=1` | 单 token 路径尝试合并等待和 RAM 专家读取内核。原有多行路径保持原逻辑。 |
| `MAYA_GLM_LOOKUP=1..7` | 使用当前请求的提示及输出后缀提出 n-gram 草稿，由原模型验证窗口接受或拒绝。成本策略可以退回单 token 解码；适合重复代码等有长串复用的文本。当前仅用于普通单请求驱动。额外窗口显存可能减少专家缓存。 |

`MAYA_GLM_LOOKUP_CHECK=1..32` 是诊断选项，会使用额外主机检查点，
逐行比较验证窗口和串行路径的全词表 logits，再比较提交后的下一步。
它会明显降低速度，仅用于隔离测试。数值对照应固定 CPU/GPU 专家执行路径，
例如为两张卡指定 `CPU_PLAN=000000000`，避免后端切换引入浮点归约差异。
诊断检查点使用 13..15 槽，勿与外部自定义检查点共用。

2026-10-25，针对频繁切换的 agent 短输出，XL 采用共享 CPU lane 12 线程、
固定 32/13 层 + MTP、5090 D 预留 256 MiB、PG500 专家池上限 26.5 GiB
（预留 128 MiB），并将会话快照放到 RAM，容量上限 4 GiB。
保留 FP16 KV / 32768 驻留窗口、252144 最大上下文、16384 prefill、148 GiB RAM 预算。
12/14/16 线程、30/31/32 分层、显存预算、RAM 快照和 64K FP16/INT8 组合均做了真实 XL 测试。
旧/新配置各两轮模拟 35K 分支 agent 请求：加权 decode 18.19 → 19.46 tok/s，
首 token 中位数 2.809 → 2.339 秒，六请求总耗时 35.736 → 31.494 秒（减少 11.9%）。
主要收益来自会话切换；短输出仍可能低于 20 tok/s。INT8 的额外收益不稳定，暂不默认启用。
12K/24K 独立样本的工具/schema 顺序变化及会话恢复检查通过。
本轮没有改推理内核或重编译，M/L 未改变。原 XL BAT 读取更新后的同一配置。
详见 [XL agent 调优与回滚配置](../bench/results/agent-tune-20261024/REPORT.md)。

2026-10-25 后续三类调优：底层预填充引擎新增
`MAYA_GLM_PREFILL_CPU_SMALL0=512`，让 5090 D 的小批次预填充也能使用现有 CPU
成本规划器。原门槛仅在 PCIe 比 CPU 固定成本慢两倍以上时才允许 CPU；新开关
在小批次下允许额外的并行 CPU 通道，分配量仍受成本和输出容量限制，超过门限保留原路径。
默认不启用；当前只在 XL 的 GPU0 设置。没有新增 CUDA 算子或改变权重量化。

同时设置 `MAYA_GLM_PCIE_SHARE0=0.25`，解码时让 5090 D 的部分 RAM 专家走快链路，
PG500 仍使用原 CPU 分担。按历史频率淘汰、加快专家回填及其组合没有可靠的额外收益，
因此专家缓存策略保持默认。KV 共同前缀驻留候选仍未启用。

约 50K 上下文、16/64/128/512/16/64-token 增量、交替恢复 A/B 的新夹具，旧/新配置
各两轮：六次预填充 12.644 → 11.184 秒，首 token 中位数 2.224 → 1.940 秒，
decode 19.04 → 19.87 tok/s，六请求总耗时 31.534 → 29.355 秒（减少 6.9%）。
这是模拟串行 agent 负载，不能直接与旧 35K 夹具比较，也不保证所有真实短输出超过 20 tok/s。
50K 分支数字召回、12K/24K 工具/schema 顺序变化与会话恢复检查通过。

## 四卡配置（2026-10-25）

实机检测为5090 D + PG500 + 5060 Ti + PG500，192GB RAM，9950X；后三卡共用Gen4 x4上行，不能把卡端x8视为独立主机带宽。XL选用gpu=[0,1,2,3]，layer_split="18,28,34"（18/10/6/11层），GPU1/2/3专家池上限28.5/13.5/27.5GiB，实际按CUDA可分配空间和保留量自动缩减。GPU0继续自动分配，reserve256MiB。共享CPU12线程、GPU0 share=.25、其余0；小增量prefill CPU<=512、prefill16384/min16、RAM会话4GiB、工具前缀规范化、FP16 KV resident32768、context262144、MTP全部保留。专家默认LRU/refill保留。

RAM预算从148调至140GiB，原因是WDDM显存与锁页RAM共同消耗Windows提交额度。50K测试最低提交余量约7GiB、可用物理内存45GiB。四卡高显存分层两轮decode27.01/27.10，合计27.06tok/s；本次同硬件双卡基线23.52，约+15%；六请求平均23.731s vs25.392s（-6.5%）。A/B召回复用49552/50114全部正确，decode专家磁盘读取为0。满262K/双并发尚未压测；M/L仅继承硬件配置，未加载测速。引擎源码/二进制未更改。原BAT继续读取JSON。
